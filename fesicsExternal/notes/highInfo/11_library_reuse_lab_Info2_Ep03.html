라이브러리와 재사용 — 검증된 코드를 조립하는 것도 실력

그래프 기능 수를 바꾸며 직접 구현(기능당 30~40줄)과 라이브러리(기능당 1~2줄)의 줄 수, 예상 버그(100줄당 1.5개), 소요 시간(줄당 5분 + 학습 시간)을 기록했습니다. 기능 6개를 직접 만들면 약 240줄·버그 3.6개·3일, matplotlib은 12줄·버그 0.2개·1시간이었고, 기능이 1개뿐이면 차이가 작았습니다. 재사용과 오픈소스·라이선스의 원리를 정리합니다.

개념 정리

1. 검증된 코드를 조립하는 것도 실력

그래프 하나를 직접 그리려면 축 눈금, 한글 글꼴, 범례, 크기 조절, 저장… 기능마다 수십 줄이 필요하고 줄이 늘수록 버그도 늘어요. 라이브러리는 수천 명이 쓰고 고친 코드라 같은 기능을 몇 줄로, 훨씬 적은 버그로 얻어요. 좋은 개발자는 "무엇을 직접 짜고 무엇을 가져다 쓸지"를 알고, 문서를 읽고 조립해요. 다만 라이선스(MIT·BSD·Apache는 자유롭게, GPL은 내 코드도 공개해야 함)를 확인해야 해요. 공짜지만 조건이 있어요.

계산해 보기

  • 그래프 기능 6개를 직접: 약 6 × 40 = 240줄, 버그 약 3.6개, 3일. matplotlib: 6 × 2 = 12줄, 버그 0.2개, 1시간.
  • 기능이 1개뿐이면 직접 40줄 vs 라이브러리 2줄 + 설치·문서 읽기 — 차이가 작아요. 기능이 늘수록 격차가 벌어져요.

2. 실험 모형과 실제의 차이

· 라이브러리도 버그·보안 취약점이 있고 버전이 바뀌면 안 돌아가기도 해요. 그래서 버전을 적어 두고(requirements.txt) 업데이트를 확인해요.

· 너무 많은 라이브러리에 기대면 프로그램이 무거워지고 의존성 충돌이 생겨요. 균형이 필요해요.

3. 생활 속에서 · 이어지는 개념

  • 공공 데이터 API 하나를 골라 문서를 읽고 데이터를 받아 그래프를 그려 보세요. 쓴 라이브러리의 라이선스를 각각 적어 보세요.
  • 오픈소스 — 리눅스·파이썬·크롬의 엔진도 오픈소스예요. 세계가 함께 만든 바퀴예요.
줄 수 = 기능 수 × 기능당 줄 수, 예상 버그 = 줄 수 × 0.015 (라이브러리 내부는 검증됐다고 봄), 시간 = 줄 수 × 5분 + 학습 시간

예제

기능 8개를 직접 40줄씩 만들면 예상 버그와 시간은?

320줄 → 버그 320 × 0.015 = 4.8개, 시간 320 × 5 = 1 600분 ≈ 27시간. 라이브러리 16줄이면 버그 0.24개·80분 + 학습.

GPL 라이브러리로 만든 앱을 팔면서 코드를 공개하지 않으면?

GPL은 내 코드도 공개해야 하는 조건 → 라이선스 위반, 법적 문제. MIT·BSD·Apache는 출처 표시만으로 자유.
